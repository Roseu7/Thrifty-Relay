<a id="design-record-for-setup-and-doctor"></a>
# セットアップとdoctorの設計記録

setupは作業ディレクトリの取得元、トンネル用APIキーの保存先、プロセスの起動方式を決めます。
doctorは、その状態についてローカル確認で分かる範囲を返します。
この文書は現在の実装と、その判断理由を記録します。
操作手順は[セットアップ](setup.md)、日常運用は[運用](operations.md)にあります。

<a id="background-and-scope"></a>
## 背景と範囲

導入では、作業ディレクトリ、Codex認証、トンネル、トンネル用APIキー、起動方式を揃える必要があります。
Windowsランチャー、設定の保存、資格情報、実行寿命、読み取り専用の診断は、それぞれ別の責務として扱います。
LinuxとmacOSはPOSIX手動起動のThriftyRelayを使い、OSの自動起動サービスとは分けます。

<a id="goals-and-out-of-scope"></a>
## 目標と対象外

導入の目標は、利用者が選んだ言語で設定を保存し、起動方式と所有者を説明し、ローカルの稼働状態を判定できることです。
手動モードで意図的に停止している状態は、設定の不具合とは別の正常な状態です。
秘密は非秘密の設定やトンネル引数へ保存せず、資格情報のバックエンド障害は必ず失敗として表示します。

次の操作や配布方法は、現在の導入経路に含めません。

- Codexへの自動ログイン
- 既存認証の移行
- トンネルの自動作成
- バイナリの自動ダウンロード
- 任意プロセスの停止
- 結果不明の自動解除
- npmパッケージの公開
- 固定のコントローラーへの自動配置
- systemdやlaunchdの登録

次の項目は、ローカルの起動状態とは別に確認します。

- ChatGPTの検出
- ホストの承認画面
- 実モデルの利用可否

<a id="decisions-adopted"></a>
## 採用した判断

| 判断 | 理由と代償 |
| --- | --- |
| 言語を最初に選ぶ | 最初の案内から読める言語を使い、保存値とOS言語をデフォルトにする |
| cwdを明示する | Codexの起動先を限定して取り違えを減らすが、OS境界にはならない |
| Codexログインは本人の確認にとどめる | 既存の認証と組織ポリシーを変更せず、実際の認証互換性は別に確認する |
| 既存のトンネルIDと実行ファイルを使う | 導入時に作成権限もダウンロードも要求しない |
| Windowsタスクを登録する | ログオン時の起動とプロセスの寿命をタスクスケジューラで管理し、登録時にUACで確認する |
| POSIXは設定保存後に明示的にstartする | ユーザーセッションの資格情報と実行寿命を確認してから起動する |
| doctorとstatusは読み取り専用にする | 診断が修復、登録、停止を伴わないようにする |
| ローカル応答と所有者確認を分ける | 応答は別プロセスからも返るため、doctorはローカル応答と記録済みの所有者を分ける |
| 未登録ポリシーをWARNにする | 従来の強制なし状態を可視化するが、終了コード0でも強制が効かないポリシーはあり得る |

<a id="windows-startup-modes"></a>
## Windowsの起動方式

`on-login-task` は本人のログオントリガーで起動するタスク、`on-demand-task` はログオントリガーなしで手動起動するタスクです。
どちらもタスク名 `ThriftyRelay MCP` と `%LOCALAPPDATA%\ThriftyRelay\Start-ThriftyRelay.ps1` を使います。
タスクは `InteractiveToken` と `HighestAvailable` で登録し、タスク方式のsetupは、登録、起動、準備完了の確認を終えてから戻ります。
`foreground` はタスクを登録せず、setup/startを実行したターミナルで稼働を続けます。
Windowsで `manual` は無効です。

[task.mjs](../../src/platform/win32/task.mjs)のActionは、両方のタスク方式で `-WindowStyle Hidden` を使うため、タスクのウィンドウは表示されません。

Windowsのフォアグラウンド実行を別のターミナルから停止する場合は、所有するターミナルでのCtrl+Cを案内します。
ターミナル終了時の子孫プロセスの完全なクリーンアップは未確認です。
基本CLIのタスク停止は、タスク停止後に8080番ポートの待ち受けプロセスと設定されたトンネル実行ファイルが一致する場合だけ、そのツリーを停止します。
この停止の保護範囲は `mcp:restart` の実行ロックより狭くなります。

<a id="posix-manual-mode"></a>
## POSIX手動モード

LinuxとmacOSのsetupは `mode: "manual"` と `taskDirectory` を保存します。
setupはmanual以外の設定を拒否し、Windowsのタスク/ランチャーアダプターへ渡しません。
手動起動のThriftyRelayは実装済みで、setupはsystemdやlaunchdのユニットを導入しません。

通常のstartはバックグラウンドのスーパーバイザーを起動し、`--foreground` は実行をターミナルへ接続します。
どちらも状態記録と所有プロセスグループを扱い、別のターミナルからのstop/restartは記録済みの所有者を確認してから実行します。
起動時の待ち受けプロセス証拠にはLinuxのssとmacOSのlsofが必要ですが、停止は記録済みのグループで扱える場合があります。
確認ではPID、開始時刻、記録の同一性を照合し、確認できない場合は実行を拒否します。
この確認はベストエフォートであり、切り離された未記録の作業は対象外です。

POSIXのThriftyRelayはUID 0での起動を拒否します。
バックグラウンド実行がターミナル終了後も続くことと、ログアウトやOS再起動の後に自動で起動することは別です。
状態ファイル、起動ロック、バックグラウンドログの場所は[運用](operations.md#state-and-logs)にまとめてあります。

<a id="doctor-checks"></a>
## doctorのチェック

[doctor.mjs](../../src/cli/doctor.mjs)と[cli.mjs](../../scripts/cli.mjs)は次のチェックを返します。
コードの一覧と読み方は[利用者向けリファレンス](setup.md#doctor-reference)を参照してください。

| ID | 設計上の責務 |
| --- | --- |
| `environment` | 実行環境とインストール済みのSDK、ネイティブバイナリを確認する |
| `config` | 設定の可読性、モード、作業ディレクトリを確認する |
| `credentials` | 選択した資格情報源の登録状態とバックエンド障害を区別する |
| `startup` | Windowsタスク、フォアグラウンド、手動モードの整合を確認する |
| `readiness` | ローカル応答と記録済みの実行状態を区別する |
| `policy` | 管理者が登録したポリシーの有無と検証状態を示す |

`POLICY_UNREGISTERED` と `POLICY_UNVERIFIED` はWARN、`POLICY_REGISTERED` はPASSです。
WARNだけの実行は終了コード0になり、終了コード0でも強制が効かないポリシーはあり得ます。
いずれかにFAILがあれば終了コード1、それ以外でUNKNOWNがあれば終了コード2です。
秘密、生の例外、コマンドラインは診断JSONの対象外です。

Windowsのdoctorは応答元を保存済みの実行所有者へ結び付けないため、応答があっても `LOCAL_ENDPOINT_UNVERIFIED` になり得ます。
POSIXは記録済みの実行状態と待ち受けプロセスの所有者が一致した場合に `RUNTIME_RUNNING` とします。
準備完了の判断材料は、OSによってこのように異なります。

<a id="credentials-and-tunnel-boundaries"></a>
## 資格情報とトンネルの境界

トンネル用APIキーはWindows Credential Manager、Linux Secret Service、macOSのログインキーチェーンへ保存します。
Linuxはsecret-toolとセッションD-Busを必要とします。
バックエンドが利用できない場合、POSIXのsetupは警告を付けて設定だけを保存します。
平文ファイルへの代替保存はありません。
`CREDENTIAL_BACKEND_UNAVAILABLE` はバックエンドやsecret-toolなどの前提が欠けている状態です。
`CREDENTIAL_BACKEND_ERROR` は別の原因でバックエンドが失敗した場合で、doctorはこれを資格情報の結果として返します。
一時的な `THRIFTYRELAY_RUNTIME_KEY` は保存されない明示的な入力経路です。

トンネルは `CONTROL_PLANE_API_KEY` を子環境で受け、非秘密の絶対NodeコマンドからMCPブートストラップを起動します。
ブートストラップは既知のトンネル資格情報と `THRIFTYRELAY_RUNTIME_KEY` による上書きを同期的に除いてから、MCP本体を読み込みます。
同じユーザーのプロセスは、除去前の初期環境や資格情報ストアを調べられる場合があります。
この対策は偶発的な継承を抑えるもので、OSのセキュリティ境界ではありません。
macOSでは、保存時に`security`コマンドの引数へキーを渡します。
この経路はMac実機で未検証です。

Codexの既存認証は公式CLIが管理します。
アダプターは現在も `auth.json` を必要とするため、キーリングのみの認証と衝突し得ます。
setupの本人確認は認証の検査ではありません。
導入は既存認証を移行しません。
トンネルとキーは公式の管理画面で作成してください。
管理者キーの入力とキー発行APIは未実装です。
配布時の外部バイナリの扱いは[第三者通知](../../THIRD_PARTY_NOTICES.md)にあります。

<a id="rejected-and-deferred-options"></a>
## 採らない案と保留した案

Windowsでタスクを使わない切り離されたデーモンは採用しません。
この判断はWindowsのフォアグラウンド実行に関するもので、POSIXのバックグラウンドスーパーバイザーは残します。
任意プロセスの一括停止、PIDの消失や時間経過だけによる結果不明の解除、資格情報の平文保存、旧方式への暗黙の切戻しも採用しません。

CLIはソースのチェックアウトから実行します。
パッケージの公開とOSの自動起動管理は、この導入経路の対象外です。

<a id="open-issues-and-verification-status"></a>
## 未解決事項と検証状態

| 対象 | 現在の根拠 | 残る確認 |
| --- | --- | --- |
| Windowsのsetup、タスク、フォアグラウンド | ソースと対応するテスト用フィクスチャがある | ターミナル終了時の完全なクリーンアップ、非昇格のコンテキスト、管理者として開いていないターミナルからのタスク操作 |
| POSIXの実行環境と状態 | フォアグラウンドとバックグラウンド、記録、待ち受けプロセス検証、Secret Serviceのテスト、CI設定がある | ログアウト境界、実機固有の条件 |
| macOSの資格情報 | `security`経由の実装とテスト用フィクスチャがある | キーチェーンとMac実機、コマンド引数へのキーの露出 |
| 認証 | ソースがauth.jsonを要求する | キーリングのみの公式認証との互換性、組織ポリシー |
| doctor | チェックの一覧と状態の分類をソースで確認済み | 実環境の全組み合わせ、Windowsの応答元の紐付け |
| 停止と復旧 | 保護付きのMCP制御と監査付きの復旧がある | 基本CLIとの保護の差、停止と新規受付の競合、部分失敗の独立した検証 |
| 設定UI | 設定項目とMCP Appsのリソースがある | 接続したホストでの表示と操作 |
| スコープ受付 | バックエンドとローカルの復旧がある | 独立した統合検証が終わるまでライブ展開を保留 |
