# ThriftyRelayのアーキテクチャ

MCPでの依頼の受付から結果の保存までの流れと、再送防止やレビュー証拠の仕組みを調べるためのリファレンスです。
ChatGPTは計画、委任、完了判定を担当します。
サーバーは受付、実行、永続化を担当します。
導入は[セットアップ](setup.md)、日常操作は[運用](operations.md)、依頼のフィールドと手順は[作業依頼](orchestration.md)を参照してください。

<a id="purpose-and-scope"></a>
## 目的と対象範囲

結果が分からない書き込みを再実行せず、実ファイルとコマンド結果からChatGPTが判断できる状態を保ちます。
対象はMCPサーバー、Codexアダプター、CLI、OS別の資格情報とプロセス操作、タスクストアです。
外部トンネル、Codex SDK/CLI、Desktop Commander、ChatGPTホストは、これらの構成要素が利用するサービスを提供します。

Windowsでは、このチェックアウトが開発ソースと稼働中MCPの起動元を兼ねます。
稼働中のプロセスは読み込み済みのコードを使い、新しく起動したワーカーは現在のファイルを読みます。
実行コードの変更や再起動の前に、稼働中の作業とロックを確認してください。
切替条件は[運用ガイド](operations.md#update-and-restart-cautions)にまとめてあります。

<a id="terms"></a>
## 用語

| 用語 | 意味 |
| --- | --- |
| トンネル用APIキー | `tunnel-client`がトンネルに接続するときに使うOpenAIのAPIキーです。setupがOSの資格情報ストアに保存します。 |
| 作業ディレクトリ | Codexが作業するディレクトリです。Codexへの依頼は、このディレクトリを基準に確認します。 |
| 一時作業領域 | 作業ディレクトリとは別のディレクトリです。`scratch: true`を付けた依頼ごとに、専用のフォルダーを作ります。 |
| タスクストア | 依頼、タスク、会話の記録を保存するディレクトリです。アンインストールしても残ります。 |
| 受付ポリシー | 管理者が登録するファイルです。Codexのサンドボックスと、承認が必要な操作を決めます。未登録のときは制限が効きません。 |
| 書き込みスコープ | Codexへの依頼が書き込むと宣言したパスです。受付で、同時に動かしてよい依頼を判断するのに使います。Codexが書き込める範囲を制限するものではありません。 |
| 結果不明 | 結果を確認できなかった書き込みです。ThriftyRelayは記録を残し、もう一度は実行しません。[復旧](recovery.md)を参照してください。 |
| 実行ロック、スコープ付きリース | 書き込みが実行中であることを示す記録です。結果不明のまま残ると、復旧するまで新しい書き込みを止めます。 |

<a id="request-lifecycle"></a>
## 要求のライフサイクル

Codex要求は1件の非同期ステップです。
`permissions=full-access` の明示、専用の絶対パスの`cwd`、永続的な `request_id` が必要です。
`cwd`は設定した作業ディレクトリの実パス、または設定した一時作業領域のサブディレクトリを指定します。
アダプターはファイルシステムのルートとユーザーのホームを拒否します。
`readOnly=true` は `CODEX_READONLY_UNAVAILABLE` で拒否します。
登録済みの受付ポリシーがある場合、ワーカーの実際のサンドボックスは要求フィールドより狭くなることがあります。
詳しくは[受付契約](admission.md)を参照してください。

受付では認証、要求形式、明示スコープ、利用枠を確認します。
利用枠はワーカーへ渡す前に読み、警告を承認する再送では直前に読み直します。
警告、停止、取得不能は別の結果であり、未知の書き込みを自動で再試行しません。
利用枠のしきい値と承認の契約は[設定リファレンス](settings.md#quota-thresholds)です。

要求の重複防止記録は実行の前に永続化します。
同じIDと同じ意図の再送は元のタスクを返し、結果出力の期限切れは再実行の理由になりません。
同じIDでの内容変更は拒否します。
スコープを省略した要求は全体排他を使い、明示した要求は共有リースを使います。
実行枠はスナップショットとワーカー起動の前に確保します。
ライブ並列受付の展開条件は[受付契約](admission.md#current-rollout-blockers)を参照してください。

ワーカーは固定のOpenAIプロバイダー、ChatGPTログイン方式、デフォルトのサービス階層を使います。
APIキーは使わず、別プロバイダーへも切り替わりません。
アダプターは `auth.json` のChatGPTトークンを確認するため、キーリングのみの認証との互換性は未解決です。
既存のAGENTS.md、Skill、MCP、プラグイン設定は作業に影響し得ます。
ワーカーの標準サブエージェント機能は無効です。
モデルとツールの利用可否は本人の権限に依存します。

<a id="model-and-conversation-compatibility"></a>
### モデルと会話の互換性

依頼では `model_role`（`base` または `upper`）を指定し、アダプターは要求を記録する前に、保存済みの `baseModel` または `upperModel` から実際のモデルを決めます。
対応するモデルと推論の強さの組み合わせは[設定](settings.md)にあります。
役割を指定しない新規要求は基本モデルを使い、継続では会話が最後に成功したモデルと推論の強さを引き継ぎます。
継続で役割を指定すると、同じ `conversation_id` のまま切り替わります。
変更に失敗しても別モデルへ切り替わりません。

現在の依存はCodex SDK 0.162.1です。
会話の記録はバージョン2、依頼の記録はバージョン3です。
それ以外の形式の依頼記録は `CODEX_REQUEST_RECORD_INVALID` で拒否し、再実行しません。
フィンガープリントには、決まったモデルと推論の強さ、明示された `write_scopes` を含めます。
旧版へのダウングレードは未検証であり、異なる実装版を同じストアで同時に動かさないでください。

<a id="waiting-for-completion-and-cancellation"></a>
### 完了待機と取消

依頼後は `remote_inspect({task_id})` で待機します。

| 設定と出来事 | 動作 |
| --- | --- |
| `wait_ms`のデフォルト | 120000ミリ秒。上限も同じ。 |
| `wait_ms: 0` | 診断用の応答を即時に返す。 |
| 実行中に待機期限へ到達 | 実行中の短い応答を返す。同じタスクIDで再び待てる。 |
| 完了通知 | 同じプロセス内で受け取る。追加推論やディスクの定期ポーリングは行わない。 |
| クライアントとトンネルの通信期限 | サーバー側の120秒とは別。 |

この待機はWorkやMCP Eventsを使いません。

完了判定は最終保存とロック処理の後に行います。
待機は最終保存の後に永続記録を読み直すため、応答は保存済みの状態を反映します。
完了したCodexタスクは回答、レビュー、使用量をまとめて返します。
`step_index` による個別の保存済み出力の取得も残しています。
一般の複数ステップタスクは要約と個別出力の契約を維持します。

待機要求の切断や取消は、その待機のタイマーとイベントの購読を解除するだけです。
作業の停止には明示した `action=cancel` または既存の実行期限を使います。
取消要求と停止確認は別であり、停止確認は既に生じた外部副作用を取り消しません。
別プロセスが所有するタスク、中断したタスク、結果不明のタスクはその状態のままで、成功扱いにも再実行にもしません。
結果不明のロックは[承認と監査を伴う復旧](recovery.md)まで保持します。

<a id="review-evidence-and-observation-limits"></a>
## レビュー証拠と観測限界

`task_type=code` では、予約した実行枠の内側でcwdの実ファイルを実行の前後にハッシュ比較します。
基準には開始時の未コミットの変更を含めるため、この差分はGitのHEAD差分とは異なります。
`expected_files` は任意の相対ファイル名の配列で、指定した場合だけ予定外の変更を分類できます。
この指定は受付の許可とは別です。
レビューJSONはタスクストアの `codex/reviews` に保存します。
結果不明のときも取得できた比較を残し、自動では削除しません。

| 証拠 | 上限 |
| --- | --- |
| ファイル比較 | ファイルを含む2000ディレクトリエントリー、合計32 MiB、1ファイル4 MiB、深さ20。 |
| 除外するパス | `.git`、`node_modules`、シンボリックリンクの追跡。 |
| SDKの`command_execution`イベント | 最大12件。各コマンドと出力は600文字まで。省略件数と切り詰めのフラグを含む。 |
| 回答 | 8000文字まで。切り詰めを明示。 |

- 上限超過、アクセス失敗、走査中の変更があると、ファイル比較は不完全になります。
- 途中で中断するとコマンド証拠が不完全になる場合があります。
- 作業ディレクトリの外のファイルと、外部サービスへの影響は比較の対象外です。
- スコープ外の変更があっても、書き込んだ主体は特定できず、`strict_scope_verified:false`を保持します。

レビューJSONには本文やGit差分を複製せず、必要な内容はread/runで確認します。
回答、ファイル比較、コマンド出力、終了コードを照合してから、ChatGPTが完了を判断します。

SDK失敗時の診断情報は、起動段階、定型の失敗種別、スレッド開始の有無、イベント数、安全なHTTPステータスに限定します。
生の例外文、スタックトレース、標準エラー出力、URL、資格情報は保存にも表示にも流しません。
ワーカーが結果を送らず終了した場合も、最後に確認できた段階と取得できた終了コードを記録します。
診断情報は原因を絞るための材料です。

使用量はSDKのトークン計数であり、プラン残量やAPI請求額とは別の値です。
完了時にはApp Serverの `account/rateLimits/read` を最大8秒で1回実行し、5時間枠と週間枠の残量割合とリセット日時を`limits`へ付けます。
応答にない枠はnull、取得失敗は `status=unavailable` とし、タスクは完了のままです。
値は別プロセスが取得したスナップショットです。

<a id="persistence-and-locking"></a>
## 永続化とロック

readとcallの画像はMCPの画像コンテンツとして返し、タスクの添付ファイルとして保存します。
テキストの文字数制限と秘匿情報のマスキングはテキストに適用し、画像データには別のバイト上限を適用します。
対応形式はPNG、JPEG、GIF、WebPです。
1画像は最大8 MiBで、各ステップとタスク全体はそれぞれ最大4枚、合計8 MiBです。
タスク出力の整理では対応する画像添付も削除します。
Code Mode内のreadはテキストだけを返します。

参加する書き込み側は同じ正規タスクストアを使います。
全体排他の `active.lock`、保守用の `maintenance.lock`、スコープ別の短い受付ゲートとリースを、それぞれ別の目的で使います。
スコープ別リースと旧バージョンの書き込み側の相互排他はブリッジで維持します。
宣言、衝突、結果不明の扱いは[受付契約](admission.md)が、解除条件は[復旧](recovery.md)が正本です。
手動エディター、別ストア、非対応の旧実装、切り離された作業はこの排他の対象外です。

タスク出力の整理は最新100件を基準とし、未完了タスク、結果不明、活動中のロックなどに対応する記録を保護します。
整理してもリクエストの重複防止記録、会話メタデータ、復旧監査は残ります。
出力の期限が切れた要求は再実行できません。
ストアを移動しても重複防止記録と監査を保持し、新しい空ストアへ旧要求を再送しません。
SDKのセッション履歴と共有キャッシュはCodexが管理します。

<a id="security-boundaries"></a>
## セキュリティ境界

cwdと書き込みスコープはOSのサンドボックスではありません。
登録済みポリシーの強制、SDKサンドボックス、実行調停、事後レビューはそれぞれ別の制御で、担う範囲も異なります。
ローカル確認と監査は同じユーザーのための材料であり、そのユーザーのアクセス権を持つプログラムは同じ証拠を読めます。

トンネル用APIキーはOSの資格情報ストア、または明示した一時的な環境変数から取得します。
トンネルの子プロセスの環境へキーを渡し、MCPブートストラップは資格情報を除いてから本体を読み込みます。
同じユーザーのプロセスは、除去前の初期環境や資格情報ストアを調べられる場合があります。
macOSのキーチェーン書き込みでは、キーを一時的にコマンド引数へ渡します。
この経路はMac実機で未検証です。
詳しい信頼モデルと報告範囲は[セキュリティポリシー](security.md)にあります。

<a id="deployment-and-execution-modes"></a>
## 配置と実行方式

Windowsはログオンタスク、手動起動タスク、元のターミナルでのフォアグラウンド実行に対応します。
LinuxとmacOSはPOSIX手動モードで、バックグラウンドのスーパーバイザーまたは `--foreground` を選びます。
setupはsystemdやlaunchdの自動起動ユニットを登録しません。
POSIXは状態、短い起動ロック、所有プロセスグループを管理し、UID 0での起動を拒否します。

ソース、認証、OSランチャー、永続タスクストアは別の場所にあります。
OS別のパスと停止条件は[運用](operations.md)に、モードの判断理由は[設計記録](setup-doctor-design.md)にあります。
`health`のソースハッシュは、起動時に読み込んだソースとディスク上のファイルとの差を確認する値です。
npmパッケージは現在非公開のため、公開後のnpx配布と固定のインストール先は未実装です。

<a id="verification-and-remaining-issues"></a>
## 検証と残る課題

静的検査、テスト用フィクスチャ、OS統合検証、実トンネル、ChatGPTの実接続、実モデル利用は別々の確認範囲です。
CIの構成と専用テスト領域の保持条件は[貢献ガイド](contributing.md)を参照してください。
キーチェーンとMac実機での動作は、CIがmacOSで動く場合でも別の確認が必要です。

未完了の項目は次のとおりです。

- 独立したスコープ並列受付の統合検証
- 部分失敗を含む復旧検証
- キーリングのみのCodex認証の互換性
- Windowsのターミナル終了時の完全なクリーンアップ
- MCP Appsと実承認カードの接続検証
公開の前にはセキュリティレビューとクリーン環境でのインストール確認も必要です。
正式な第三者セキュリティ監査は未実施です。
