# 結果不明の実行の復旧

復旧は、保持された実行ロックまたはスコープ付きリースを調査し、プロセス、ファイル、外部への影響のレビューを確認できる場合にだけ行います。
復旧はレビュー済みの受付バリアを解放します。
変更はそのまま残り、元のタスクの結果は変わらず、要求は再実行できないままです。
正常な作業の取り消しや、不明な結果を避けた再起動のために使わないでください。

切り離された作業が停止したことは、プロセスの識別情報と子孫の検出で確認します。
記録されていない切り離し済みのジョブ、外部アプリケーションやサービスへ送信済みの操作、作業ディレクトリ外の効果は、運用者自身がレビューしてください。
確認と監査は運用上の記録であり、ユーザーのアクセス権をすでに保持しているプロセスに対する認証境界ではありません。

<a id="inspection-before-recovery"></a>
## 復旧前の調査

影響を受けた実行環境と同じタスクストアを使います。
Windowsのデフォルトのタスクストアは、PowerShellで次の読み取り専用の調査を実行します。

~~~powershell
node scripts/remote-maintenance.mjs inspect --task-dir "$env:LOCALAPPDATA\ThriftyRelay\tasks"
~~~

この低水準のコマンドには、絶対パスの`--task-dir`が必要です。
LinuxとmacOSは[OSごとのパス](operations.md#state-and-logs)を、独自の保存先ではsetupで保存したパスを指定します。

- 調査は、ロックのハッシュ、保存済みのプロセス識別情報、現在のプロセス証拠、保持情報、存在する場合はスコープ付きのサマリーを返します。
- 切り離し済みのジョブと外部サービスは、この一覧とは別に確認します。
- タスク、要求、会話、ロック、リース、レビュー、監査の記録を保持します。
- `active.lock`、`maintenance.lock`、`admission.lock`、リースファイルは、レビュー済みの復旧で解放するまで残します。

承認の前に、それぞれの証拠を確認してください。

<a id="processes"></a>
### プロセス

記録済みのPIDと起動IDを、現在のワーカーや子孫プロセスと比較します。
所有する作業の停止を確認し、記録されていない作業や切り離された作業も調べます。

<a id="files"></a>
### ファイル

タスク開始前の基準と実際の変更を比較します。
影響を受けた可能性がある、次のファイルも含めてください。

- 生成されたファイル
- 未追跡のファイル
- 無視対象のファイル
- Git外のファイル
- 作業ディレクトリ外のファイル

<a id="external-operations"></a>
### 外部操作

次の操作を確認します。

- ネットワーク要求
- サービスとアプリケーション
- デプロイ
- キューに入っている操作や、切り離された操作

不明点は不明のまま記録し、ロールバック済みと判断しないでください。

トンネル用APIキー、トークン、生の資格情報出力、その他の秘密情報を証拠に含めないでください。
Gitの状態と差分のサマリーはレビューを助けます。
ただし、無視対象のパスは対象外で、誰が変更したかも示しません。
従来のガイド付きプレビューはThriftyRelayのチェックアウトを使います。
影響を受けた別の作業ディレクトリは別に調査してください。
スコープ付きプレビューはスコープ付き作業ディレクトリを使います。

<a id="guided-recovery"></a>
## ガイド付き復旧

~~~sh
thriftyrelay recover
~~~

保存先を`~/thriftyrelay-tasks`に設定したインストールでは、そのストアを明示します。

~~~sh
thriftyrelay recover --task-dir "$HOME/thriftyrelay-tasks"
~~~

| 項目 | 動作 |
| --- | --- |
| ストアの選択 | `--task-dir`、`THRIFTYRELAY_TASK_DIR`、[OSごとのデフォルト](operations.md#state-and-logs)の順。 |
| 確認入力 | 入出力がローカルの対話型ターミナルであることが必要です。無人承認用のフラグはありません。 |
| 表示言語 | `--lang ja`または`--lang en`。 |
| 復旧方式 | 観測したストアからスコープ付きか従来方式かを選びます。方式間の変換はしません。 |

setupが保存した`taskDirectory`は自動では読みません。
続行する前に、選ばれたストアが実際のインストールと一致することを確認してください。

<a id="scoped-lease-procedure"></a>
## スコープ付きリースの手順

ガイド付きの経路は、不明なリース、または記録された所有者が停止した実行中のリースを、残りの安全検査に合格した場合に受け付けます。
レジストリ内にリースが1件だけあり、復旧可能な候補が1件だけあることが条件です。
他のリースが残っている間は拒否し、解放順序を選ばずにすべてのリースを保持します。

1. 名前空間、レジストリとブリッジのハッシュ、タスクID、リースID、要求ID、会話ID、所有者、記録されたプロセスを確認します。
2. 求められたら、表示されたとおりのタスクIDとリースIDを入力します。
   部分的または一致しない選択は拒否されます。
3. プロセス、ファイル、外部への影響の証拠を確認します。
   記録されたワーカーや子孫が稼働中の場合、所有タスクがアクティブな場合、証拠が取得できない場合は解放を拒否します。
4. 確認の直前に、新しく取得したプロセス一覧を確認します。
   検査を終えた後に大文字の `YES` を入力します。
   それ以外の回答は承認を取り消します。
5. バックエンドに、制御、レジストリ、ブリッジのハッシュと名前空間、リースとブリッジのトークン、タスク、要求、会話の関係とファイルハッシュ、プロセス証拠を再検証させます。
   承認後にプロセス集合が変わっていた場合は拒否します。
6. 最終結果と監査IDを確認します。
   コマンドは選択したバリアが消えたことを検査します。
   部分失敗のコードが返った場合は、原因を調べてから次の操作を判断してください。

解放の前に、バックエンドは監査の開始記録を `codex/recovery/<audit-id>.json` に保存します。
タスクは `interrupted` と `execution_unknown:true`、要求は `reviewed_unknown`、会話は `interrupted` として記録されます。
短い受付ゲートの下で、選択した最後のリースとブリッジを解放し、その後 `guard_state: "recovered"` を記録します。
タスクの結果は元のままで、要求は再実行できないままです。

<a id="legacy-procedure"></a>
## 従来の手順

従来のグローバル実行ロックがある場合、`thriftyrelay recover` は紐づくタスク、ロックのハッシュ、保存済みの識別情報、現在のプロセス証拠、レビューチェックリストを表示します。
ガイド付きフロントエンドは、PIDが存在しない場合でも、未完了のタスクレコードや実行中のタスクを拒否します。
レビューの後、`y` または `yes` を大文字小文字を区別せずに受け付けます。
スコープ付き復旧の大文字 `YES` とは異なります。
バックエンドは正確なロックとプロセス証拠を再検査し、メンテナンスゲートを保持します。
解放前に監査の開始記録を書き込み、関連レコードを更新して、監査の完了記録を書き込みます。
不明な効果は不明のままで、元の要求は再実行できません。

別にレビューした従来のレコードや不完全なレコードには、低水準の手順を使えます。
Windowsのデフォルトのストアでは、次を実行します。

~~~powershell
node scripts/remote-maintenance.mjs recover --task-dir "$env:LOCALAPPDATA\ThriftyRelay\tasks" --approval "$HOME/thriftyrelay-recovery-approval.json"
~~~

レビュー済みの承認レコードを`~/thriftyrelay-recovery-approval.json`として保存してから実行します。
承認レコードは正確なタスクIDとロック全体のSHA-256に紐づき、運用者の識別情報または参照、プロセス、ファイル、外部への影響の証拠を含みます。
従来の識別レコードや不完全な識別レコードには、[recovery.mjs](../../src/mcp/recovery.mjs) で定義された明示的な従来プロセスレビューの証明も必要です。
ローカルのターミナルでは、表示されたとおりの `UNLOCK <task_id> <first-12-lock-hash>` フレーズを入力します。
ガイド付きの拒否を回避するために承認レコードを作らないでください。
原因を解決し、必要な別のレビューを先に受けてください。
従来のバックエンドは、スコープ付きのブリッジやレジストリの状態を `REMOTE_SCOPED_RECOVERY_UNAVAILABLE_ROLLOUT_BLOCKED` で拒否します。
スコープ付きの状態にはスコープ付き手順を使ってください。

<a id="refusal-and-partial-failure-reference"></a>
## 拒否と部分失敗のリファレンス

| 条件またはコード | 対応 |
| --- | --- |
| `REMOTE_LOCAL_INTERACTIVE_CONSOLE_REQUIRED` | ローカルのTTYから実行してください。確認は自動化しないでください。 |
| `REMOTE_MAINTENANCE_LOCKED_INSPECT_REQUIRED` | ゲートを保持し、所有者と監査の開始記録を調査してください。通常の復旧はゲートを削除しません。 |
| `REMOTE_SCOPED_OTHER_LEASES_ACTIVE` | すべてのリースをそのまま残してください。現在の復旧は複数のリースから1件を解放できません。 |
| `REMOTE_SCOPED_SELECTION_MISMATCH` | 意図したタスクとリースを再調査してください。近似のIDで代用しないでください。 |
| `REMOTE_OWNER_TASK_STILL_ACTIVE`、`REMOTE_SCOPED_LEASE_OWNER_ACTIVE` | 所有作業が停止したことを確認してください。経過時間やPIDの不在だけでは不十分です。 |
| `REMOTE_OWNED_PROCESS_STILL_ALIVE` | 先に、所有作業を承認された経路で停止してレビューしてください。 |
| `REMOTE_PROCESS_EVIDENCE_UNAVAILABLE` | 証拠収集の環境を修復してください。子孫の列挙が不完全だと、Windowsの256階層の上限を含め、プロセスを見落とすことがあります。 |
| `REMOTE_LOCK_CHANGED`、`REMOTE_PROCESS_EVIDENCE_CHANGED` | レビューしたスナップショットが古くなっています。状態を保持し、新しい承認の前に調査してください。 |
| `REMOTE_SCOPED_RECORD_MISMATCH`、`REMOTE_RECOVERY_RECORD_UNAVAILABLE` | 欠落、不整合、読み取り不能なレコードは、ロック解除では修復できません。 |
| `REMOTE_HUMAN_APPROVAL_REQUIRED` | 解放には正確なローカル確認が必要です。 |
| `REMOTE_RECOVERY_AUDIT_UNAVAILABLE` | 解放には永続的な監査の開始記録が必要です。 |
| `REMOTE_RECOVERY_POST_RELEASE_RECORD_FAILED` | スコープ付きの解放は終わりましたが、最終的なタスク記録は未確認です。追加の書き込みの前に、監査とストアを調査してください。 |
| `REMOTE_RECOVERY_AUDIT_UPDATE_FAILED` | スコープ付きの解放は終わりましたが、最終的な監査更新は未確認です。報告された監査IDと証拠を保存してください。 |

復旧がメンテナンスバリアを残してクラッシュした場合は、別に承認されたメンテナンス操作の前に、所有者と監査を調査してください。
復旧に参加するすべてのThriftyRelayラッパーの処理を終え、1人の運用者が操作してください。
タイムアウトでバリアを削除しないでください。
所有者の不在を、すべての効果が停止した証拠として扱わないでください。
無人で実行できる強制ロック解除はありません。

<a id="limits-and-rollout-status"></a>
## 制限とロールアウトの状態

スコープ付き復旧、プロセス証拠、部分失敗、監査の整合性についての独立した動的検証は、ライブロールアウトの阻害要因のままです。
ここで説明したプロセス証拠はベストエフォートです。
切り離された作業の追跡は不完全で、Mac実機での復旧動作は対象外です。
復旧レコードは、対応する要求の重複防止記録とともに保持してください。
宣言と強制の違いは[受付](admission.md)、永続化は[アーキテクチャ](architecture.md)、保護付き再起動は[運用](operations.md)を参照してください。
