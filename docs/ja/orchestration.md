# Codexへの作業依頼

ChatGPTに、接続先のPCで動くCodexへ作業を渡すよう依頼します。
ThriftyRelayは依頼を記録して実行し、回答、コマンドの結果、ファイルの変更記録を返します。

<a id="your-own-steps-and-codex"></a>
## 自分で行う作業とCodexに頼む作業

ChatGPTは、Codexを使わずに`remote_task`のステップで、PC上の作業を直接行うこともできます。

| 作業 | 使うもの |
| --- | --- |
| ファイルを見る、何かを探す | `read`または`search` |
| 場所が分かっている小さな変更 | `edit`、`write`、`patch`。そのあと`read`で確かめる |
| コマンドを実行して結果を伝える | `run`。時間がかかるコマンドは`execution: "async"` |
| 原因を調べる、複数のファイルを変える | 1件の`codex`ステップ |

`run`には作業ディレクトリを指定する項目がないので、コマンドの中でディレクトリを移動します。

<a id="task-description"></a>
## 依頼内容

対象の作業ディレクトリ、期待する結果、変更してよい範囲、完了を確認する方法を伝えます。
たとえば、次のように依頼します。

~~~text
設定された作業ディレクトリをCodexで確認し、プロジェクトの構成を説明してください。
ファイルは変更せず、失敗したコマンドがあれば報告してください。
~~~

変更を頼む場合は、対象のファイルや機能と、実行してほしい確認を指定します。
コードの作業では`expected_files`を指定すると、返されたレビューで予定外の変更を分類できます。
書き込み範囲の宣言と同時実行の制限は[受付](admission.md)を参照してください。

<a id="model-selection"></a>
## モデルの選択

依頼ではモデルではなく役割を指定します。
どのモデルと推論の強さを使うかは、依頼を受け付けた時点の`baseModel`と`upperModel`の[設定](settings.md)で決まります。

| 依頼 | モデルの選択 |
| --- | --- |
| 新規会話で`model_role`を省略 | 基本モデル。 |
| `model_role: "base"` | 基本モデル。 |
| `model_role: "upper"` | 上位モデル。`upperModel`が`disabled`のときは`CODEX_UPPER_MODEL_DISABLED`で拒否します。 |
| 継続で`model_role`を省略 | その会話が最後に使ったモデルと推論の強さ。 |
| 選択に失敗 | エラーを返し、前回成功した選択を保持する。 |

普段の作業には基本モデルを使います。
`model_role: "upper"`は、具体的な未解決の問題、繰り返す失敗、利用者の依頼があるときだけ指定します。

<a id="request-fields"></a>
## 依頼のフィールド

Codexへの依頼は、`remote_task`の`execution: "async"`と、1件の`kind: "codex"`ステップを使います。

| フィールド | 用途 |
| --- | --- |
| `prompt` | 作業の内容。 |
| `cwd` | アダプターが受け付ける、既存の作業ディレクトリの絶対パス。 |
| `permissions` | `"full-access"`を指定します。ワーカーのサンドボックスは登録済みポリシーが選びます。 |
| `request_id` | その依頼内容に固有のID。同じ内容の再送でも維持します。 |
| `model_role` | 普段の作業は`base`、根拠のある切り替えは`upper`。 |
| `task_type` | `question`、`research`、`code`。`code`はファイル変更のレビューを有効にします。 |
| `conversation_id` | 既存のCodex会話の継続。 |
| `expected_files` | レビュー用の、作業ディレクトリからの相対ファイル名。省略できます。 |
| `write_scopes` | [受付](admission.md)で説明する書き込み範囲の宣言。省略できます。 |

作業ディレクトリには、設定した場所と実体パスが一致するディレクトリ、または設定した一時作業領域のサブディレクトリを指定します。
ファイルシステムのルートとユーザーのホームは拒否します。
Codexへの依頼では`scratch: true`と`readOnly: true`を拒否します。
Codexを読み取り専用で実行するには、登録済みポリシーで`read-only`のサンドボックスを選ぶ必要があります。

<a id="approval"></a>
## 承認

承認期間を使う受付ポリシーでは、full権限レベルの承認カードで保留中の依頼を1件承認します。
利用枠の警告では、プランの残量を確認して続行に同意します。
この2つの承認は別々に扱います。
カードは[受付](admission.md)、利用枠の警告、停止、取得不能の結果は[設定](settings.md#quota-thresholds)を参照してください。

利用枠の警告を承認した後の継続は、同じ`request_id`と依頼内容を維持し、発行された承認トークンと同意のフラグを追加します。
依頼内容を変更する場合は、新しいリクエストIDを使います。

<a id="waiting-and-cancellation"></a>
## 待機とキャンセル

1. タスクを1回送信し、返された`task_id`を保持します。
2. そのIDを指定して`remote_inspect`で完了を待ちます。
3. まだ作業中なら、同じIDで再び待ちます。

`wait_ms: 0`は調査用に現在の状態をすぐ返します。
待機の接続が切れても、タスクは動き続けます。

Codexタスクが完了すると、回答、レビュー、使用量をまとめて返します。
`step_index`では、`expose`を指定した`read`や`call`の画像を含む、保存済みの出力を取得します。
通信期限と保存の順序は[アーキテクチャ](architecture.md#waiting-for-completion-and-cancellation)にあります。

キャンセルする場合は、同じタスクIDと`action: "cancel"`で`remote_inspect`を呼びます。
返された状態で停止を確認してください。
すでに生じた変更や外部への影響は、そのまま残ります。

<a id="result-review"></a>
## 結果の確認

`succeeded`と`codex: PASS`は、エージェントの応答が完了した記録です。
実ファイル、コマンドの出力、終了コード、`review.summary.complete`を依頼の条件と照合して、完了を判断します。
保存されたレビューは`review.path`で確認し、変更したファイルは対象を絞ったGitの状態と差分で確認します。
説明のない変更、確認の失敗、不完全なレビュー、結果不明の実行は調査が必要です。

`usage`はSDKのトークン使用量です。
`limits`は、タスクが終わったあとに読み取った5時間枠と週間枠の残量割合とリセット日時です。
利用枠の警告と停止には、依頼を送る前に読み取った値を使います。
取得できない値はnullまたは取得不能として返します。

<a id="continuation-and-recovery"></a>
## 継続と復旧

通信の都合で同じ内容を再送する場合は、リクエストIDを維持し、既存のタスクを取得します。
新しい修正には新しいリクエストIDを使い、観測した失敗と期待する結果を伝えます。
同じCodex会話で修正を続けられます。

実行結果が不明な場合は、既存のタスクとファイルを調査してから、次の書き込みを依頼します。
出力の保持期間が過ぎたりロックを復旧したりしても、元のリクエストは再実行されません。
保持されたロックとリースは[復旧](recovery.md)を参照してください。

別のチャットで続ける場合は、次を引き継ぎます。

- 元の目的、許可したディレクトリと操作、完了条件。
- タスク、リクエスト、Codex会話のID。
- 関係する変更とコマンド結果。
  合格した確認も含めます。
- 未解決の失敗と、結果が分からない外部への影響。

<a id="skills"></a>
## Skill

作業手順を選ぶ際は[Skillのカタログ](skills.md)を使います。
起動時のカタログに入るのは、`~/.codex/skills`のグローバルなユーザー管理のSkillだけです。
メタデータと本文は、利用者の指示と既存の権限の範囲で、信頼しないデータとして扱います。
