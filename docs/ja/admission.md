<a id="admission-and-write-scopes"></a>
# 受付と書き込みスコープ

アクセス規則の設定、承認カードの確認、Codexの書き込み範囲の宣言に使うリファレンスです。

受付は、要求を開始してよいか、参加するどの書き込み主体が重なってよいかを判断します。
任意のフルアクセス作業が宣言されたパス内に収まるかどうかは、この判断の外側です。
管理者が登録したポリシー、タスクの書き込みスコープ宣言、実行後のレビュー証拠は分けて扱ってください。

<a id="administrator-registered-admission-policy"></a>
## 管理者が登録する受付ポリシー

ポリシーの登録はsetupとは別の操作です。

| 登録状態 | doctorの結果 | サーバーの動作 |
| --- | --- | --- |
| 未登録 | `WARN / POLICY_UNREGISTERED` | ポリシー適用なしの従来動作。 |
| 有効な登録 | `PASS / POLICY_REGISTERED` | ポリシーを適用。 |
| 既存の登録を読み取れない、または検証できない | `WARN / POLICY_UNVERIFIED` | 受付を停止。 |

登録は明示的なローカル管理者操作です。

~~~sh
thriftyrelay register-policy --file "$HOME/thriftyrelay-policy.json"
~~~

レビュー済みのポリシーを、ホームディレクトリの`thriftyrelay-policy.json`として保存してから実行します。
登録コマンドは通常のユーザーで実行します。
スクリプトがWindowsとPOSIXで管理者権限への昇格を要求するため、`sudo`は付けません。
ThriftyRelay自体は非rootユーザーで実行します。
セットアップ修復のついでに登録を行わないでください。
検証済みの登録場所は `C:\ProgramData\ThriftyRelay\policy.json`、`/etc/thriftyrelay/policy.json`、`/Library/Application Support/ThriftyRelay/policy.json` です。
ポリシーを準備する前に、[ポリシースキーマと検証](../../src/platform/policy.mjs)と[登録CLI](../../scripts/register-policy.mjs)を参照してください。

サーバーは、既知のパス操作と特権ステップ種別を登録済みポリシーの下で評価します。
Codexでは、ポリシーの権限レベルがワーカーのサンドボックスを選択します。

| 権限レベル | サンドボックス | 登録 |
| --- | --- | --- |
| standard | `read-only` | 公開の権限レベル。 |
| trusted | `workspace-write` | 内部の対応付け。 |
| full | `danger-full-access` | 公開の権限レベル。 |

公開Codex要求は引き続き `permissions: "full-access"` を要求し、`readOnly=true` を拒否します。
その要求フィールドは、登録済みポリシーが選ぶより狭いサンドボックスを上書きしません。

シェル、任意ツール、コードモードのステップは、パス宣言で実行時ターゲットをすべて記述できないため、full権限レベルを要求します。
すでに承認されたフルアクセスの子プロセスは、保護パスにも到達できます。

<a id="policy-fields"></a>
### ポリシーのフィールド

| フィールド | 値 |
| --- | --- |
| `generation` | 正の整数。下書きでは1を指定し、登録時に現在のポリシーから次の世代を割り当てます。 |
| `kill_switch` | trueでfull権限を停止する真偽値。 |
| `full_access` | モードと、正の整数の`max_minutes`と`max_concurrent`。`denied`モードでは上限値を省略できます。 |
| `tunnel_ids` | このインストールで許可するトンネルIDの、空でない配列。 |
| `workspace_roots` | 通常のファイルアクセスに使う絶対パスの、空でない配列。 |
| `scratch_roots` | 一時ファイルのアクセスに使う絶対パス。省略できます。 |
| `protected_paths` | サーバー自身のファイルに加えて保護する絶対パス。省略できます。 |

ポリシーの例を共有する場合は、トンネルIDを除いてください。

<a id="policy-modes"></a>
### ポリシーのモード

| `full_access.mode` | 動作 |
| --- | --- |
| `window` | 依頼1件に紐づく承認でfull権限を使います。 |
| `persistent` | 承認期間を設けず、常時full権限を使います。 |
| `denied` | full権限を許可しません。 |

`kill_switch: true`は、モードにかかわらずfull権限を停止します。
`window`モードでは、`max_minutes`が承認の有効時間、`max_concurrent`が同時に保持できる承認の件数上限です。
承認回数に日次上限はありません。
廃止された`max_per_day`は、新規登録では省略し、既存の値も無視します。

<a id="approval-cards"></a>
### 承認カード

1. `remote_task`が`APPROVAL_REQUIRED`とタスクIDを返します。
2. `open_approval`でその依頼を開きます。
   カードには予定のパスが表示され、ステップの本文は展開時に読み込みます。
3. 承認または拒否を選びます。
   サーバーは記録をほかの操作と競合しない形で確保し、申請から10分の期限を再検査します。

| 判断と失敗 | 結果 |
| --- | --- |
| 承認 | タスクIDとステップに紐づく承認期間を開いて消費し、同じIDの非同期タスクを開始します。 |
| 拒否、期限切れ | 承認期間を開かずに依頼を終了します。 |
| 申請後に一時作業領域が変更された | 依頼を無効にして再申請を求めます。 |
| 承認期間を開けない | 保留中に戻して再試行を受け付けます。 |
| 承認の消費に失敗 | 調査用に確保済み記録を保持します。 |
| `TASK_START_FAILED` | 承認は消費済みです。タスクIDと保持された確保済み記録を調べてから次の操作を判断します。 |

アプリ専用の`pending_approvals`、`approval_step`、`approve_task`、`decline_task`が一覧、詳細、操作を提供します。
拒否、期限切れ、無効化の判断は24時間、最大100件まで残ります。
保存済みの判断は、削除されずに残った確保済み記録より優先されます。
タスクも判断もない確保済み記録は「処理中または未確認」と表示し、保留中の記録と競合する場合は操作を拒否します。
受付の承認は、[利用枠警告への同意](settings.md#quota-thresholds)や[復旧の承認](recovery.md)とは別です。

<a id="temporary-work-area-and-scratch_roots"></a>
## 一時作業領域と`scratch_roots`

セットアップは、ユーザーごとの一時作業領域を作成し、その絶対位置を `tempWorkspace` として保存します。
これは作業ディレクトリルートとも内部のタスクストアとも別です。
OS別のデフォルトのパスは[運用](operations.md#state-and-logs)にあります。
明示的な `THRIFTYRELAY_TEMP_WORKSPACE` が最優先で、次に保存済みの `tempWorkspace`、その後にプラットフォームのデフォルトが使われます。
デフォルトは場所にすぎず、それ自体では受付を変えません。

登録は、絶対パスの配列である任意の `scratch_roots` でオプトインします。

~~~json
{"scratch_roots": ["C:\\Users\\example\\AppData\\Local\\ThriftyRelay\\temp"]}
~~~

分類順序は、保護、機密、scratch、作業ディレクトリ、外部です。
scratchルート内の `.env` のような名前は機密のままで、保護パスは保護のままです。

登録済みのscratchルート内での通常の `read`、`write`、`edit`、`patch` ステップには、承認期間は不要です。
`run`、`code`/`call`、Codexのステップは引き続き既存の権限レベルを要求します。
scratchパスでフルアクセスが与えられることはありません。
すべてのscratchルートの外にあるパスは、既存の動作を維持します。

<a id="scratch-paths"></a>
### 一時領域のパス

通常の要求で`scratch: true`を指定すると、`<tempWorkspace>/<task_id>/`と、そのタスクを示す`owner.json`を作成します。

| パス | 解決方法 |
| --- | --- |
| 相対の`path`、`file_path`、`cwd`、`patch.files[].path` | タスクのディレクトリ内で解決。 |
| `run.command`の`{{scratch}}` | タスクのディレクトリに展開。 |
| 絶対パス | 書き換えず、通常の受付チェックを適用。 |
| `{{scratch}}/..`を含む、外へ出る相対パス | カードの作成前に`SCRATCH_PATH_ESCAPE`で拒否。承認は消費しない。 |
| シンボリックリンクとジャンクション | 実行時に実体のパスを再分類し、その対象の権限レベルで判定。 |

standardとtrustedでは、次を拒否します。

- 別タスクの所有者記録があるディレクトリ。
- 存在するが所有者記録がない兄弟ディレクトリ。
- scratchルートそのもの。
  兄弟タスクを検索できてしまうため、`ADMISSION_SCRATCH_ROOT_SCOPE`で拒否します。
  自身のディレクトリか、ルート直下のファイルを指定してください。

fullではフルアクセスの動作が適用されます。

Codexはscratchルートのサブディレクトリを絶対パスの`cwd`として受け付け、ルート自体は拒否します。
ポリシーが選ぶサンドボックスは変わりません。
`scratch: true`は`CODEX_SCRATCH_UNSUPPORTED`で拒否するため、実行先と整理対象が食い違わないように`cwd`を使ってください。

<a id="scratch-retention"></a>
### 一時データの保持

| 状態 | 保持と整理 |
| --- | --- |
| 成功を確認済み | 自身のscratchディレクトリを削除します。 |
| 失敗 | 保護されていないデータを最大7日間保持します。同期と非同期の両方の結果に`Scratch retained: <path>`を表示します。 |
| 削除可能なデータが100件または1 GiBを超えた | 両方の上限を満たすまで、古いものから削除します。 |
| 実行中 | 整理と両方の上限の対象外です。 |
| `guard_state=unknown`、`execution_unknown`、復旧証拠あり | 整理の対象外です。 |
| タスク記録があるが読めない、または解析できない | 未解決の可能性があるため保持します。ストアで不在を確認できた記録だけが、孤立記録として期限切れの対象になります。 |

整理するのは、ルート直下で名前がタスクIDと一致し、`owner.json`も同じタスクを示すディレクトリだけです。
リンクはたどりません。
タスク履歴にも同じ保護規則を使い、ディレクトリが残る間は復旧済みや未解決の記録を保持します。
アンインストール後も一時データは残るため、別に確認してください。

<a id="explicit-write_scopes-contract"></a>
## 明示的なwrite_scopes契約

この宣言を持てるのは、1件の非同期Codexステップだけです。
cwdからの相対のファイルまたはディレクトリ、あるいはリテラル文字列 `"global"` を使用してください。

~~~json
{"write_scopes": [{"kind": "file", "path": "src/example.mjs"}]}
~~~

~~~json
{"write_scopes": [{"kind": "directory", "path": "src/feature"}]}
~~~

~~~json
{"write_scopes": "global"}
~~~

宣言の配列は1〜100件のエントリを含み、各エントリは `kind` と `path` だけを持ち、各パスは最大240文字です。
ディレクトリとその走査対象の内容は、すでに存在し、検証可能でなければなりません。
ファイルは、親が存在すれば新規でもかまいません。
絶対パス、トラバーサル、ワイルドカード形式のパス、リンクとリパースポイント、ハードリンクされたファイル、未対応のファイル種別、検証できないパスは拒否されます。
`.git`、`node_modules`、共有設定は、個別の宣言やそれを含むディレクトリ宣言では分離できません。

書き込まれ得る生成ファイル、テスト成果物、コマンド出力はすべて宣言してください。
共有設定、依存関係のインストール、Gitの変更、制限できない効果にはグローバル受付が必要です。
これは呼び出し側の義務です。
パスを宣言しても、OSの書き込み境界は強制されません。
`expected_files` は、後続のレビュー向けに期待される変更を記述するだけです。
スコープを推測したり、書き込みを許可したり、リースを予約したりはしません。

明示的な宣言はv3要求フィンガープリントに含まれるため、異なる宣言で要求IDを再利用しないでください。
フィールドを省略すると、既存のv3および従来のv2の照合規則が維持され、従来の全体排他が使われます。
検証可能な形で無効な宣言は、要求の重複防止記録より前に拒否され、受付の競合はワーカー起動より前に失敗します。
自動の実行キューや、競合する要求の自動再試行はありません。

<a id="concurrency-and-locks"></a>
## 並行性とロック

参加するすべてのプロセスは、同じ正規のタスクストアと互換性のある実装を使用する必要があります。
短時間の `admission.lock` がレジストリの変更を直列化します。
リースはワーカーより前、かつレビュー用作業ディレクトリのスナップショットより前に予約されます。
`active.lock` のスコープ付きブリッジは、スコープ付きリースが存在する間、従来のグローバル書き込み主体を排除します。
通常の読み取りと検索のステップは並行のままでかまいません。
従来の書き込み主体は、読み取り専用と自称して協調的な排除を迂回できません。

| 組み合わせ | 受付の動作 |
| --- | --- |
| 重複しない明示的なファイルまたはディレクトリのスコープ | バックエンドは `maxCodexAgents` まで並行リースを許可できます。デフォルトは3で、範囲は1〜5です。 |
| 交差するファイルまたはディレクトリのスコープ | 拒否されます。ディレクトリスコープは子孫を含みます。 |
| グローバル宣言、または従来のグローバル書き込み主体 | 参加するスコープ付き書き込み主体とは排他になります。 |
| 同じCodexの `conversation_id` | ChatGPTの会話やMCPプロセスをまたいでも、並行にはなりません。 |
| 不明なリース、不明なレジストリ状態、メンテナンスバリア | 調査されるまで、新しい書き込みと保護された再起動をブロックします。 |

新しい会話IDは受付より前に作成されるため、そのIDも排除に参加します。
ワーカーのPIDは実行を進める前に永続化され、識別証拠は起動時、スレッド通知時、間隔を空けた進捗イベント時に更新されます。
プロセス証拠の永続化に失敗した場合はワーカーの停止を要求し、不明なリースを保持します。
子孫プロセスが停止したことを確認してください。
通常の応答やNodeラッパーの終了だけでは、それを示せません。
観測されない切り離し済みの作業を完全に追跡することはできません。

実装は [scope-leases.mjs](../../src/mcp/scope-leases.mjs)、[adapter.mjs](../../src/codex/adapter.mjs)、[task-manager.mjs](../../src/mcp/task-manager.mjs) にあります。
手動のエディタ、無関係なツール、別のストア、古い実装、外部サービスの操作は、この協調の保証範囲外です。

<a id="declaration-versus-enforcement"></a>
## 宣言と強制の違い

書き込み範囲は、参加する書き込み側の競合を調整します。
Codexのサンドボックスは、登録済みポリシーが別に選びます。
full権限の子プロセスや同じユーザーのプログラムは、宣言した範囲外のファイルにもアクセスできます。

コードタスクのレビューは `admission.outside_declaration_observed` と `strict_scope_verified:false` を報告します。
レビューはcwd内の前後ハッシュを比較するため、cwd配下のファイルが変わったことを示せます。
並行する1人の書き込み主体への帰属、厳密な準拠、外部の副作用には別の証拠が必要です。
レビューは `.git` と `node_modules` を除外し、[アーキテクチャ](architecture.md)に記載されたファイル、バイト、深さの上限を持ちます。
観測されたスコープ外の差分を、追加の証拠なしに特定のワーカーによる証明済みの違反と見なさないでください。

<a id="current-rollout-blockers"></a>
## 現在のロールアウト阻害要因

スコープ付きバックエンドと、リース単位のローカル復旧は実装済みです。
スコープ付き並行実行のライブ展開は、独立した統合テストが揃うまでブロックされたままです。
これは運用上のロールアウト制限であり、機能フラグで有効化するものではありません。
スキーマが存在する、MCPを再起動した、対象を絞ったテストが通った、という理由だけでライブの並行要求を有効化しないでください。

残る独立検証には、プロセスをまたぐ並行書き込み主体、不明および部分失敗の経路、最後のリースの復旧拒否動作、プロセス証拠の変化、監査の整合性が含まれます。
復旧手順は、他のリースが残っている間は意図的に選択を拒否します。
Windowsのプロセス観測では、POSIXの復旧動作や切り離されたプロセスの停止は確認できません。
証拠要件には[復旧](recovery.md)、保護付き再起動の条件には[運用](operations.md#windows-mcp-control)を参照してください。
